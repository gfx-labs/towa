# Store: the session directory backend and the benchmark harness

2026-11-11

## What was built

- `src/store/dir`: the first `store.Store` backend.
- `src/store/storebench`: a harness any `store.Store` can be run through.
- `src/config/store.go`: `store.root` and `store.compression`.

## Layout

```
<root>/<session id>/meta.json        the session's Meta
<root>/<session id>/log.jsonl        every entry, one JSON value per line (compression none)
<root>/<session id>/log.jsonl.zst    the same lines, one zstd frame per Append (compression zstd)
<root>/<session id>/blobs/<sha256>   content stored by PutBlob
<root>/<session id>/torn-<offset>    bytes Repair set aside
```

Nothing of a session is outside its directory, and the store holds no state in memory: every call opens what it needs. Copying the directory under another root moves the session. `TestMovedSessionContinues` copies a session directory to a new root, starts a second process on it (the test binary run again), and has that process load the context, read the full history, open a blob and append an entry. It runs for both log formats, and the second process is configured with the other compression than the session has.

## Decisions

- **One write and one fsync per `Append`.** The entries of an append are encoded into one buffer and written with one `WriteAt`, then the file is synced. The directory is synced only when a name changes: `Create`, `SetMeta`, `Delete`, the first `PutBlob`, each new blob, `Repair`.
- **`Updated` is not written on append.** The contract says `Append` sets the session's `Updated` time. Rewriting `meta.json` durably costs a write, a file fsync, a rename and a directory fsync, so three more syncs a turn. `Load` and `List` return the time of the last entry in the log as `Updated` instead. `meta.json` holds the value from `Create` until the first entry.
- **A session keeps the format it was created with.** `store.compression` applies to `Create`. A store reads and appends to either format, so changing the setting, or moving a session to a host with another setting, needs no conversion. A directory with both log files is reported as corrupt.
- **Locking is `flock` on the log file.** Appends and `SetMeta` take it exclusively, readers take it shared for the moment they read the size. It orders several processes on one root. `TestConcurrentAppendsKeepEveryEntry` runs eight stores on one session. `syscall.Flock` exists on Linux and macOS, so there is no `_linux.go` file. It is advisory, and it does nothing useful on NFS.
- **A reader sees the log as it was when the call was made.** `Load` and `History` record where the log ended and read up to there, so an append during a read is not half seen. The file is opened when the sequence is ranged over.
- **Torn tail.** A crash during `Append` can leave part of a record. `Load` and `History` yield every whole entry and then a `*dir.TornError` with the offset. `Append` refuses with the same error. `Repair` copies the torn bytes to `torn-<offset>`, syncs, and cuts the log back. Nothing is dropped without the caller asking. `TestTornTailIsReported` cuts the log at every byte of an append.
- **A failed write is taken back.** When the write or the fsync of an append fails, the log is truncated to its size before the call, so the error does not leave a torn record behind.
- **Damage that is not a torn tail** (a line that does not decode, a frame that does not decompress, a marker that is not one) is a `*dir.CorruptError` with the path and offset.
- **Blobs.** `PutBlob` writes to a temporary file in `blobs/` while hashing, syncs it, renames it to the hex digest and syncs the directory. Content the session already holds is not written again. `OpenBlob` verifies the hash: the reader hashes as it is read, and the read that would return `io.EOF` returns a `*dir.CorruptError` when the digest differs. A caller that stops reading early gets no verdict. The hash string is the only caller text that becomes a path, so it must be `sha256:` and 64 lowercase hex digits.
- **Validation on write.** `Append` rejects an entry with no id or an item that fails `Item.Validate`, before anything is written. `Create` rejects a nil id and a relative `Cwd`.
- **`Create` and `Delete` rename.** A session is built under `.<id>.creating` and renamed into place. `Delete` renames to `.<id>.deleting` and then removes. A crash leaves a whole session or a hidden directory that `List` skips. Nothing sweeps a leftover hidden directory yet, except a later `Create` or `Delete` of the same id.
- **Ids and times come from the caller.** The store makes neither.

### The compressed format

Each `Append` is one record: a 24 byte marker, a zstd frame holding the JSON lines, and the marker again. The marker is a zstd skippable frame (RFC 8878 section 3.1.2), so the file is an ordinary zstd stream: `zstd -dc log.jsonl.zst` prints the JSON lines. Checked with zstd 1.5.7 on a three-append session.

The marker holds the frame's length, the number of entries and a flag for "holds a compaction". With it:

- `Load` walks the markers back from the end to the latest record flagged as holding a compaction, and decompresses from there.
- `History` with a `From` skips whole records by their count without decompressing them.
- A torn tail is a last record whose two markers do not match.

In the plain format `Load` reads lines back from the end until it finds a compaction entry. A line is checked for the bytes `"compaction":` and decoded only when it has them, because a tool input or a provider's opaque value can contain the same bytes. `TestLoadStartsAtTheLatestCompaction` has such a decoy, and a line longer than the read buffer.

### A limit of the plain format

The plain log has no record around an append. A crash that tears an append of several entries exactly between two lines leaves a log that looks whole and holds the first entries of an append that never returned. The compressed format does not have this: an append is one record or none. The test names the case. The loop lane should not assume an append is atomic across entries when `store.compression` is `none`.

## Config

| key | default | validation |
|---|---|---|
| `store.root` | empty, which means `$XDG_STATE_HOME/acpharness/sessions`, or `~/.local/state/acpharness/sessions` when `XDG_STATE_HOME` is unset or relative | absolute when set |
| `store.compression` | `zstd` | `none` or `zstd` |

A default cannot hold an environment variable, so `config.Store.Dir(environ)` resolves the directory. With no root, no absolute `XDG_STATE_HOME` and no absolute `HOME` it returns an error.

## Measurements

Machine: i9-14900, Linux 6.12, btrfs on NVMe (TEAM TM8FP4004T), mounted `rw,relatime,ssd,discard=async,space_cache=v2`. Eleven other workers were building on the same machine (load average about 5), so the append times moved between runs. The sizes and counts are exact.

Workload: 2000 turns, each a prompt, five tool calls (thinking with a 256 byte random signature, the call, a 4000 byte result), an answer and a usage entry. 18 entries and about 31 KiB a turn, 36000 entries and 58.9 MiB in all. The text is cut from the Go 1.27.3 `net/http` sources (158 files, 3.1 MiB), so results repeat within a session the way file reads do. Reads are the median of five, each on a new store value.

```
ACPHARNESS_STOREBENCH_CORPUS=$(go env GOROOT)/src/net/http \
ACPHARNESS_STOREBENCH_ROOT=$HOME/.jcode/scratch \
ACPHARNESS_STOREBENCH_TURNS=2000 ACPHARNESS_STOREBENCH_TOOL_CALLS=5 \
ACPHARNESS_STOREBENCH_RESULT_BYTES=4000 ACPHARNESS_STOREBENCH_KEYWORD=RoundTripper \
go test -v -count=1 -run TestRunByHand -timeout 25m ./src/store/storebench/
```

| fsyncs per turn | 1 | 1 |
| bytes written / payload | 1.000 | 0.351 |
| bytes on disk | 58.9 MiB | 20.6 MiB |
| append, mean / p50 / p99 | 1.88 / 1.76 / 5.01 ms | 2.17 / 1.96 / 5.42 ms |
| heap in use after the appends | 1.2 MiB | 3.0 MiB |
| load, 36000 entries, no compaction | 404 ms | 348 ms |
| bytes allocated by that load | 112.3 MiB | 111.0 MiB |

| read the full history | 268 ms | 346 ms |

What they say:

- Write amplification is 1.0 for the plain log and 0.35 for zstd. There is no index, snapshot or second copy.
- An append is one fsync, and the fsync is the cost: about 1.8 ms here. Compression adds about 0.2 to 0.3 ms to a 31 KiB turn.
- Appending each entry on its own costs 18 fsyncs a turn and about 36 ms. The loop should append once per turn, or once per step, not once per entry.
- `Load` after a compaction does not depend on the session's length.
- A load with no compaction decodes the whole log. Its 112 MiB of allocation is the decoded entries: decoding is 1.9 times the payload.
- The store holds 1.2 MiB of heap with the plain format, which is the harness and runtime, not per session. The zstd encoder and decoder add about 1.8 MiB once per process, made on first use. `WithLowerEncoderMem` gave 2.7 MiB against 3.0, inside the run to run difference, so it is not set.

### zstd: kept, and the default

- The session is 2.9 times smaller on disk (20.6 against 58.9 MiB). A runner that uploads the directory moves that much less.
- It costs about 0.2 ms a turn against a 1.8 ms fsync, and 1.8 MiB of heap per process.
- Reading the full history is about 25 to 30 percent slower (357 against 276 ms). The scan was 6 percent slower in the first run and 45 percent in the second (412 against 284 ms).
- Reading a range near the end is four times faster, because whole records are skipped by their markers. The plain format has to read every line before the range.
- An append is atomic across its entries, which the plain format is not.
- With one append per entry the ratio drops to 0.49 and reads take 1.7 times as long, because each small frame is compressed alone. If the loop ends up appending per entry, `none` is the better setting and the default should be looked at again.

The corpus is source code. Sessions with mostly images or already compressed output will compress less. The number to re-measure is on recorded real sessions, once the loop writes them.

### The pooled encode buffer

`Append` encodes into a `bytebufferpool` buffer, and the zstd frame into a second. A probe in a scratch module encoded a turn of 17 entries with 4 KB of text each into a new `bytes.Buffer` and into a pooled buffer (`go test -bench Encode -benchmem -count 3`):

| | ns/op | B/op | allocs/op |
|---|---|---|---|
| new buffer | 88411 to 105438 | 263494 | 45 |
| pooled | 61988 to 68332 | 1103 | 34 |

The probe uses a two-field struct, not `transcript.Entry`, and is not in the repo. The pooled buffer is kept.

## Tests kept

`src/store/dir/dir_test.go`: the moved session in a second process, load from the latest compaction and history ranges, the torn tail at every byte with `Repair`, a damaged record, concurrent appends from eight stores, blobs (dedup, not found, a bad hash string, changed content), and the session calls (`Create`, `SetMeta`, `List`, `Delete`, not found).

`src/store/storebench/storebench_test.go`: the harness run on the directory backend with `docs/` as the corpus, checking the counts it reports (entries, one fsync a turn, the entries in context after a compaction, the same hits from both formats), and `TestRunByHand` behind `ACPHARNESS_STOREBENCH_CORPUS`.

Scratch probes were removed. There is no test file for `src/config/store.go`: `Dir` and `validate` were checked with a throwaway test (the four environment cases, a relative root, an unknown compression, the loaded default).

## Not done

- SQLite, Postgres and the length-prefixed binary log from the design's list. They are not in this lane.
- No crash was produced with a real power cut or a killed process. The torn tail test writes the prefixes a crash can leave. It does not prove what a file system leaves.
- Nothing was run on macOS. The darwin build passes. On macOS `File.Sync` is `F_FULLFSYNC` in Go, which is far slower than Linux `fsync`: the append numbers above do not carry over.
- No garbage collection of blobs that no entry references, and no sweep of `.creating` and `.deleting` leftovers.
- `List` opens every session and reads its last entry. It was not measured on a root with many sessions.
- `History` by range reads from the start in the plain format. There is no offset index.
- The harness does not measure blobs.
- `docs/design.md` still shows the old `Snapshot` method and lists backends to evaluate. The coordinator owns that file.
