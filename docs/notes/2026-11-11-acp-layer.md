# ACP layer: generated types and our own connection

2026-11-11

`src/acp` is the ACP implementation: types generated from the pinned schema (1.31.0, in `src/acp/schema`) and a hand-written JSON-RPC connection. It does not import `coder/acp-go-sdk`. `docs/design.md` ("ACP layer") gives the reason.

## Generator

`tools/acpgen` is a copy of the SDK's generator at commit `492745b`. Its README lists every change. Three were bugs found by running it against schema 1.31.0:

- `CreateElicitationRequest.Validate` read a field the union type does not have. The package did not compile.
- Every required string was rejected when empty. The schema says `required`, which means present. Only `Notice.title` has a `minLength`. With the upstream rule an agent could not write an empty file: `fs/write_text_file` with `content: ""` returned `Invalid params`. Checked by running `TestEmptyRequiredStringIsAccepted` against types generated with the old rule: it fails with `content is required`.
- Union `MarshalJSON` had 20 blocks of unreachable code after a `return`, which `go vet` reports.

The generator is deterministic: two runs give identical files, so CI can diff them.

## Connection

`connection.go`, about 400 lines, no dependency outside the standard library.

- Framing: one JSON message per line. A line is read whole whatever its length (`bufio.Reader.ReadBytes`, not `bufio.Scanner`, which stops at 64 KiB by default). Prompts carry files and images inline and the protocol sets no limit.
- Requests each run on their own goroutine. A `session/prompt` handler calls back to the client (`fs/read_text_file`, `session/request_permission`) and must be able to read the answer.
- Notifications and responses are handled on the reading goroutine, one at a time, in the order read. That keeps `session/update` in order for a client. A notification handler therefore cannot wait for a response: a request sent with its context returns `ErrWaitInNotification` instead of deadlocking.
- `Arrival(ctx)` gives each inbound message's position in the read order. Requests run concurrently, so this is how an agent tells whether a `session/cancel` came before or after a given prompt. The SDK tracked one cancel func per session inside the generated dispatch. We removed that: the session owner needs the ordering anyway to make a new prompt cancel the running one.
- `$/cancel_request` cancels the context of the named inbound request. The handler's `context.Canceled` becomes error `-32800`. A caller whose context ends sends `$/cancel_request` and returns without waiting for the peer.
- Unknown notifications are ignored and logged at debug, as the spec's extensibility page says. Unknown requests get `-32601`.
- A response with neither `result` nor `error` fails the waiting call. It is not answered: answering a response with an error would start a loop with a peer that does the same.
- Outbound JSON does not escape `<`, `>` and `&`. The messages are mostly source code, and the default escaping turns each of those into six bytes.
- `Serve` returns when the reader ends. It then cancels running handlers and waits for them. Cancelling its context does not interrupt a blocked read: the owner closes the reader.

## Tests

`connection_test.go` drives a real agent side and client side over `io.Pipe`, or the agent side with raw JSON lines. The tests run in `testing/synctest` bubbles, so a message that never arrives fails as a deadlock at once instead of timing out. Run 20 times under `-race`: pass.

## Dependencies

- `github.com/stretchr/testify` (tests only): the assertion library acphost and jobshop use.
- `github.com/dave/jennifer` (in `tools/acpgen` only): the vendored generator is written with it. It is not in the acpharness module.
