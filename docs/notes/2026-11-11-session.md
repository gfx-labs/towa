# Session lane: client capabilities, modes, config options, commands

2026-11-11

Built in `src/session` and `src/config/session.go`. The rule of the package is unchanged: only what is implemented is advertised, a method behind a capability that is not advertised answers Method not found, and a field that would be dropped is refused with `-32602`.

## What was built

| part | where | behaviour |
|---|---|---|
| Client capabilities | `gate.go` | `initialize` stores the client's capabilities in a `Gate`. `Agent.Gate()` returns it |
| Update gating | `Gate.Sendable`, `Agent.send` | `notice` needs `session.notices`. `compaction_update` and `compaction_summary_chunk` need `session.compaction`. `plan_update` and `plan_removed` need `plan`. `subagent_update`, `session_message` and `session_message_chunk` need `subagents`. Every other type is always sent |
| Modes | `registry.go`, `agent.go` | `auto` and `ask`. `session/new` returns `modes`. `session/set_mode` switches |
| Permission | `Agent.permit`, passed as `loop.Turn.Permit` | In `ask` mode a tool with effect `Writes` or `Executes` goes through `session/request_permission` with allow once, allow always and reject |
| Config options | `Registry.AddConfigOption` | `configOptions` on `session/new`, `session/set_config_option`. `mode` is registered |
| Commands | `Registry.AddCommand` | `available_commands_update`. `/mode` is registered |
| `session/new` fields | `Agent.NewSession` | `additionalDirectories`, `systemPrompt`, `mcpServers`, initial `configOptions`, `_meta.acpharness` |
| Unstable methods | `agent.go` | `session/status`, `session/options`, `session/set_title` |
| Prompt content types | `Supports.Prompt` | `image`, `audio`, `embeddedContext` |

## Decisions

- The mode is one value with two names. It is the `mode` config option, and `session/set_mode` sets that option. A change sends `current_mode_update`, and also `config_option_update` unless the request was `session/set_config_option`, whose response already carries the options. A request that sets the value the session already has sends nothing.
- `Turn.Sendable` is exposed as well as the gate inside `Turn.Update`, so the loop can pick a fallback (`plan` in place of `plan_update`) before it builds an update. `Update` returns nil for a gated type. That is the one place something is not sent, and it is the protocol's rule, not a fallback of ours.
- A boolean config option is listed and settable only for a client that advertised `session.configOptions.boolean`. For any other client it keeps its default and setting it answers `-32602`, as an unknown option does.
- "Allow always" covers the tool's name for the rest of the session. Changing the mode clears it, since it was granted in the mode it was asked in. `reject_always` is not offered: nothing would act on it yet.
- Cancellation of a pending permission request works from both ends. A `session/cancel` cancels the turn's context, the connection sends `$/cancel_request` for the permission request, and the prompt answers `cancelled`. A client that answers the request with the `cancelled` outcome before its `session/cancel` arrives stops that one turn, which also answers `cancelled`.
- `Supports` is how the wiring says what the turn acts on. The agent carries `additionalDirectories`, `systemPrompt` and `mcpServers` to `loop.Turn` in every case, and advertises each only when its `Supports` field is set. With it unset the field is refused. The default is all off, because `loop.Stub` uses none of them.
- `systemPrompt` needs `Supports.SystemPrompt`. It is checked at `session/new` with `agentctx.Build`, the function that later builds the prompt, so the check and the use cannot differ. Its `UnsupportedModeError` and `ContentError` answer `-32602` and no session is created. The capability advertised is `agentctx.Capabilities()` (append and override). `src/session` does not call `agentctx.Load`.
- `mcpServers`: stdio needs `Supports.MCP` to be non-nil, http and sse need their flag. The `acp` transport is always refused and never advertised.
- `_meta.acpharness` on `session/new` is read against the registered `Override` keys. A key that is not registered is an error. Other keys of `_meta` (`traceparent`) are not ours and are left alone. `mode` is registered always. `context_files` and `skills_dirs` (lists of paths, carried unchanged to `loop.Turn.ContextFiles` and `loop.Turn.SkillsDirs`, loop commit 72b564c) are registered when `Supports.ContextOverrides` is set, which the wiring does once it merges them into `config.Context`. The other keys in the design (model, limits, mcp servers, compaction) are registered by the packages that own them.
- Initial `configOptions` follow the spec, which differs from `session/set_config_option`: an unknown id, a wrong type and a value that is not allowed are ignored (logged at debug), and a repeated id is `-32602`. `sessionCapabilities.options` covers both this field and `session/options`.
- A config option and an override reach the turn through a function that writes a `loop.Turn` field (`ConfigOption.Apply`, `OverrideEffect.Turn`). There is no map of settings on the turn. The model option is then one `AddConfigOption` call plus the `Turn` field the loop lane adds for it.
- A command with a `Run` function is answered by the session and the turn does not run. A command without one is only listed, and the prompt goes to the turn, which handles it (`/compact`, `/model`, `/cost` will be of this kind or get a `Run` from their package). A prompt whose first text block does not name a registered command is an ordinary prompt.
- `available_commands_update` is sent once per session, before the first later request that names the session is handled (`prompt`, `set_mode`, `set_config_option`, `set_title`). It cannot go out earlier: the update carries the session id, and a handler cannot write after its own response. `session/status` and `session/options` send nothing, as the spec requires.
- `session/status`, `session/options` with a `sessionId` and `session/set_title` depend on whether the agent has a store: see "Stored sessions" below. Without one, status answers `open` or `-32002`, options with a `sessionId` answers `-32602`, and the title lives in memory.
- `session/set_title` trims surrounding white space and rejects an empty result. No length limit is applied: nothing configured or measured gives one.
- `session.mode` (default `auto`) is the mode a new session starts in. `NewAgent` fails on a value that is not a mode.

- A prompt that a hook denies answers `-32600` Invalid request, with a typed stop of kind `harness.StopDenied` in the error's `data` and the hook's reason in its `message`. The turn did not start, so it is the request that was refused, not the agent that failed. Both forms the loop may use are handled: `*loop.DeniedError` and a `*loop.StopError` of that kind.

## Agreed with other lanes

- `loop` (commit b006b8c): `loop.Turn` has `Dirs`, `SystemPrompt`, `McpServers`, `Client`, `Sendable` and `Permit`. The loop calls `Permit` once before every tool call with the tool's name, its effect and an `acp.ToolCallUpdate`. False means rejected. An error stops the turn.
- `acp-layer`: `acp.AfterResponse(ctx, fn)` is on the `acp-layer` branch. Once it is on master, `NewSession` can send the commands right after its response and `announce` can go.

## Stored sessions

`Options.Store` (a `store.Store`) and `Options.Mapper` (the `loop.Mapper` the turn shows items with) are optional. With `Store` nil nothing below is advertised and `session/load`, `session/resume`, `session/list` and `session/delete` answer Method not found. With it, `initialize` advertises `loadSession` and `sessionCapabilities.resume`, `list` and `delete`.

| method | behaviour |
|---|---|
| `session/new` | creates the session in the store at once, so a session with no turn yet can be listed, titled and loaded. The loop's own create-if-missing then finds it |
| `session/load` | checks the session and the `cwd`, replays every stored entry through the `Mapper` in stored order, sends the title and time as `session_info_update` and the commands, then answers with `modes` and `configOptions`. The session is then live here |
| `session/resume` | the same without the replay |
| `session/list` | stored sessions, oldest first, with `cwd`, title, `updatedAt` and additional directories. `cwd` filters. Subagent sessions (those with a parent) are left out |
| `session/delete` | closes the session if it is live here, then deletes it from the store |
| `session/status` | `open` in memory, `saved` in the store only, `-32002` in neither |
| `session/set_title` | written through `SetMeta` before the answer. Works for a session that is in the store and not in memory, as the schema allows, and then sends no update, since no connection is attached to it |
| `session/options` with `sessionId` | what load would answer: the stored mode and model. A `cwd` that differs is `-32602` |

Decisions:

- The replay reads `History`, not `Load`: every entry ever appended, including those a compaction took out of the model's context, because the client saw them. `Load` is used only for the `Meta`. Nothing is read into memory beyond one entry at a time.
- A `cwd` that is not the stored one is `-32602` with both paths in `data`. A session id that is not a UUID cannot be in the store and is `-32002`, like one that is missing.
- The request's `additionalDirectories` is the session's whole list from then on, as the schema says, and is written to the store.
- Mode and model are stored in `Meta` on every change and restored on load. The order is: defaults, stored values, the request's `_meta.acpharness`, the request's `configOptions`. A stored value this process cannot use (a model it does not have configured) fails the load with `-32602` and names the fix, a value in `configOptions`. It does not fall back to the default.
- Loading a session that is already live in this process. The schema does not say. `session/status` says a client that did not create or resume a session on its own connection "MUST still call `session/load` or `session/resume`", so a load of a live session is a normal request and must succeed. It is treated as a fresh attach from the store: the running turn is cancelled and waited for, as `session/close` does, and the session is rebuilt from the store and replayed. Nothing durable is lost, since entries are stored as they are made. What only the process knew is dropped: the tools allowed "always", and the `_meta` overrides of the request that created the session, which the new request replaces.
- Loads, resumes and deletes run one at a time per agent, so two loads of one session cannot both install it.
- The cursor of `session/list` is the id of the last session of the page before. Ids are UUIDv7 and the store lists them in order, so a session created or deleted between two pages neither repeats nor hides another. The page size is `session.list_page_size`, default 0, which means one page: no measurement says where a page should end. The store reads every session's meta for each page, so paging bounds the response, not the work.
- `archived` on `session/list` is `-32602`: the capability is not advertised.

Not kept across a load, because `store.Meta` has no field for them: the `systemPrompt`, the `mcpServers` and the `_meta.acpharness` overrides (`context_files`, `skills_dirs`). The client sends them again on load, which the schema says it should for the system prompt. A load without them runs the session without them.

A session whose log has a torn tail, which a process killed in the middle of an append can leave, is not recovered here. `session/load` replays the whole entries, then fails with `-32603` on the store's `*dir.TornError`, and the session is not made live. `session/resume` does not read the log, so it succeeds and the next turn fails when it appends. The fix is `(*dir.Store).Repair`, which is not on `store.Store`. Whether a load should repair on its own is a contract decision, since repair sets bytes aside. Not tested here.

`session/fork`, `session/archive` and `session/unarchive` stay Method not found. The store has no archived flag in `Meta` and no way to copy a session's entries and blobs to a new id as one operation. A fork built here from `History`, `Create` and `Append` would not carry the blobs' directory and would not be atomic, so it is left to the store.

Checked:

- `TestStoredSessionIsLoadedByAnotherAgent`: one agent runs two turns, sets a title and a mode, and records a compaction. A second agent with its own `dir.Store` on the same directory reports `saved`, lists the session, refuses a wrong `cwd` and a prompt before the load, then loads. The replayed updates equal, as JSON, what the first agent's client was sent plus the two prompts, in order, from before the compaction on. The mode is restored, a prompt continues, a second load replays the longer history, and a delete is seen by both agents.
- `TestResumeTitleASavedSessionAndListInPages`: resume without replay, a title on a saved session, two pages and a refused cursor.
- `TestSessionMovesToANewProcess`: two real processes. The test binary starts itself as an agent on standard input and output over the store directory. The first runs a turn, sets a title and exits. The second loads, replays the same updates and takes a prompt. `src/cli` does not pass a store to the agent yet, so this is the session package with the real store across processes, not the `acpharness` binary.

Limits of these checks: the turn in the tests is a test turn that appends entries and shows them through `loop.Mapper`, as `loop.Run` does, without a model. The real loop was not run. A live turn also sends updates the store does not hold (text deltas in several chunks, a tool call's `in_progress` status, the tool's own content such as a diff), so a replay of a real turn shows the same conversation in fewer and plainer updates, which is what `Mapper.Updates` documents. The plan and usage are not replayed unless the `Mapper` produces them.

## Not done

- `session/fork`, `session/archive`, `session/unarchive`: Method not found, see above.
- Auth: `logout` answers Method not found. `authenticate` answers `-32602` for every method id, since none is advertised.
- Not implemented and not advertised: `providers/*`, `auth/status`, the `acp` MCP transport, elicitation. The client's `fs`, `terminal` and `elicitation` capabilities are recorded and passed to the turn in `Turn.Client`. Nothing calls those client methods yet.
- The `/compact` and `/cost` commands. Each is a registration.
- A changed command list is not sent again. The registry is fixed when the agent is made.
- The conformance run against `acp-go-sdk` v0.13.5 as the client.
- `pkg/acp` moves to `encoding/json/v2` on the `acp-layer` branch: decoding becomes case-exact and `acptest.Message` fields become `jsontext.Value`. The tests here already use v2 and exact member names, but they have not been run against that branch.

## Sessions across connections

### Fork, archive and retained settings

With a store, fork and archive are advertised. Fork copies the whole stored
history and blobs using `Store.Fork`, creates an independent ID and attaches it
without replay. It does not cancel the source. Archive closes a live session on
any connection before setting its archived flag. Unarchive changes visibility
without attaching. List defaults to exclude archived sessions and supports
`include` and `only`, rejecting unknown filters. Forks are ordinary listed
sessions, not subagents.

The checked-in schema's new, load and resume requests all carry cwd, additional
directories, MCP servers, system prompt, config options and `_meta`. There is no
new-only protocol field. `Meta.State` holds custom config values, turn-shaping
overrides and a retained system prompt as JSON bytes. Named mode/model metadata
remains authoritative. An omitted system prompt keeps the stored one. Explicit
request overrides replace stored override keys. Additional directories and MCP
servers are always the request's complete resulting list. MCP configuration is
not stored. Always-allow permissions are connection-local. Stored values or
overrides unsupported by the new process fail instead of being dropped.

The fork/archive test drives two ACP connections of one host over the directory
store, checking independent history, archive visibility, ownership loss and
unarchive without attachment. The retained-settings test uses a fresh agent over
the same real store, checking custom config, context overrides, a retained system
prompt and a mode changed after the original override. Race tests and lint pass.

Load and resume now call `Store.Repair` after stopping any previous owner's
turn and before replaying or answering. A repair logs a warning with the session
ID and byte count, increments `acpharness.session.repairs`, and reports
`_meta.acpharness.repair.setAsideBytes` on the response. A whole log adds no
response metadata. Repair errors fail the request, not a silent empty replay.
`TestTornSessionMovesToANewProcess` cuts an actual compressed log after a whole
turn and inside the next append. Another test-binary process loads or resumes,
reports the exact bytes set aside and appends a new turn successfully. Race
tests, vet and lint pass on the shared checkout with the directory backend.

`NewHost(Options)` owns the registry, store and live session table once per
process. `Host.NewAgent()` makes one agent per connection. `NewAgent(Options)`
still makes an independent host and agent for stdio callers. The listener can
call `Host.ServeConn(ctx, conn)`, which builds the ACP connection and closes the
agent when serving ends. The caller still closes the transport to free blocked
reads. No peer identity is interpreted by the session package.

Load and resume take over a session from any connection of the host. They remove
it from the old connection, cancel its turn and wait before rebuilding it from
the store. The old connection gets an unknown-session error for subsequent
prompts. Status can report another connection's live session without attaching
it. Closing a connection cancels its turns and removes its live sessions, but
does not delete the stored sessions. Locks for attach, delete and title changes
are per session and are discarded when no caller holds or awaits them.

`TestSessionMovesBetweenConnectionsOfOneProcess` drives real ACP pipe connections
against one host and a directory store. It checks takeover during a running
turn, refusal of prompts from the old connection, disconnect during a turn,
saved status and a later resume and replay. Existing cross-process tests remain
the owners of durability coverage. This is not a listener socket test.

- `src/cli/cli.go`: build one `session.Registry`, let the packages add to it, and pass it as `Options.Registry`. Set `Options.Supports` from what the loop, the context builder, the MCP client and the provider act on.
- `src/cli/cli.go`: pass `Store` (a `dir.Store` on `config.Store.Dir`) and `Mapper` (the loop's, with its tool set and context sizes) to `session.NewAgent`. Until then `serve` advertises no stored-session method.
