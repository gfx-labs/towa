# Tools lane: capabilities, repair, gating, batch

2026-11-11

One implementation per capability, as plain Go functions with typed input and a typed result. Nothing here has a model-facing name, schema or wording. The dialect adapters wrap these in the next wave.

## What was built

| package | entry points | does |
|---|---|---|
| `src/tools/fsops` | `Read`, `Write`, `ApplyEdits`, `Roots` | line-range read with image and binary detection, whole-file write, exact string replacement (one or many edits) |
| `src/tools/shell` | `Run` | one command in its own process group, output streamed through `Env.Progress`, timeout, cancel |
| `src/tools/search` | `Grep`, `Find` | text search and file listing over `rg` |
| `src/tools/repair` | `Compile`, `Schema.Apply` | the listed argument repairs, then schema validation |
| `src/tools/gate` | `Split`, `Apply`, `Estimate` | withholds a result over the token budget |
| `src/tools/batch` | `Run`, `Outcome` | several calls in one, scheduled by `Effect` |
| `src/tools/content.go` | `TextContent` | text as `acp.ToolCallContent` |
| `src/config/tools.go` | `Tools` | every limit and timeout used above |

A failure the model can act on is a typed error (`*fsops.Error`, `*shell.Error`, `*search.Error`, `*repair.InvalidError`, `*batch.Error`) with a `Kind` and the numbers an adapter needs to write the upstream message. Any other error means the harness could not do the operation.

## Decisions

### Path confinement is off by default (changed after review)

The first version refused every path outside the working directory and the additional directories. The coordinator had it changed, for three reasons: `docs/design.md` leaves sandboxing to the host, the shell reaches every path anyway so the check protected nothing, and the upstream Read description tells the model it can read any file on the machine.

- `tools.files.confine` (default `false`). Off: read, write, edit, the shell `Dir` and the search path take any absolute path, and a relative path is taken from `Cwd`.
- On: a path that ends up outside every session directory, once symbolic links are followed, is `KindOutside`. This is the first version's behaviour unchanged.
- `Roots.Contains(path)` says whether a path is inside the session directories whatever the setting. Nothing in this lane acts on it. It is for the adapters and the permission prompt.
- There is no third mode.

File access goes through `os.Root` in both modes. Inside a session directory the root is that directory, so a link swapped in after the check cannot lead out. Outside, the root is the path's parent, or the deepest directory of it that exists when the file is new.

A link that points nowhere cannot be written through in either mode: the write fails rather than create the link's target.

### fsops

- Read counts lines by `\n`. A last line without a newline is a line. The range is refused whole (`KindTooLarge`) when it is over `read_max_bytes`. It is never cut.
- Binary: a NUL byte in the first 8000 bytes (git's rule), or text that is not valid UTF-8. Latin-1 files are therefore refused as binary. An adapter that needs to read them needs a decision on encodings first.
- Image: `http.DetectContentType` on the first bytes, for PNG, JPEG, GIF and WebP. The extension is not used.
- Write and edit put the content in a temporary file beside the target and rename it. A reader sees the old content or the new. The cost: the file gets a new inode, so other hard links keep the old content, and owner and extended attributes are not carried over. The mode is kept.
- Edit: each edit sees the result of the ones before it. `Old` must occur exactly once unless `All` is set. Any failing edit means nothing is written. Edits that leave the file as it was are `KindNoChange`.
- `Change.Diff()` returns the ACP diff content (old and new text). No unified diff text is produced: ACP clients diff the two texts themselves. An adapter whose upstream tool prints a patch has to render one.

### shell

- `Setpgid` puts the command in its own group. Cancel and timeout send `SIGKILL` to the group. There is no `SIGTERM` first and no grace period.
- A process that leaves the group (`setsid`) is not killed. It can also hold the output pipe open, so reading stops `pipe_wait` after the command has ended and the result sets `PipeHeld`.
- Standard output and standard error share one pipe, so their order is kept and they cannot be told apart afterwards.
- `Result.Started` is false only when the context was already cancelled before the command was started. `Result.Outcome()` maps that to `cancelled`, a cancel after the start to `unknown`, a timeout or a non-zero exit to `failed`.
- Output over `tools.max_output_bytes` keeps the first half and the last half and reports `DroppedBytes`. The client still gets all of it through `Progress`.
- Each `Progress` call carries only new output, cut so that a multi-byte character is not split. A `Progress` error stops the streaming, not the command, and is returned in `Result.ProgressErr`.
- The command inherits the harness's environment and has no standard input.

### search

- `rg` is looked up with `exec.LookPath` on every call. Missing is `KindNoRipgrep` with a message that says how to fix it. There is no fallback.
- Lines mode reads `rg --json`, so paths and lines that are not UTF-8 survive. Files and counts modes read NUL-separated output.
- `--no-config` is always passed, so a user's `RIPGREP_CONFIG_PATH` cannot change results. Results are sorted by path, which makes `rg` single-threaded.
- `rg` does not follow symbolic links. A link out of the tree is not searched unless it is the search path itself.
- `Limit` and `Offset` count result lines, context lines included. Results past `tools.max_output_bytes` stop the search and set `Cut`.
- `rg` exit status 2 with nothing on standard error means some files could not be read: the result is returned with `Unreadable` set. With text on standard error it is `KindInvalid` (a bad pattern, glob or type).

Outline and trace modes are not built. The design says they need a separately specified implementation. Nothing here claims `rg` can do them.

### repair

The repairs are the design's list and nothing else: a list or an object sent as a JSON string, one object where a list is declared, a number or a boolean sent as a string. A repair is made only where the value's type is one the schema does not take, so a string stays a string wherever a string is allowed. Each repair is returned as a `Repair{Kind, Path}`. This package does not count or log: the caller does, with the returned list.

- An argument with no repairs is returned byte for byte. A repaired one keeps the member order and the text of every untouched value.
- Validation is `github.com/google/jsonschema-go`. It was enough. It ignores `format`, by its own documentation.
- To find a value's schema the walker follows `properties`, `additionalProperties`, `items`, `prefixItems`, `allOf`, `anyOf`, `oneOf` and local `$ref` into `$defs` or `definitions`. It does not follow `if`/`then`/`else` or `patternProperties`: a value under those is not repaired and is still validated.
- A string holding `null` is not repaired.

### gate

- The estimate is the result's text bytes divided by `bytes_per_token`, rounded up. Images and audio are not counted.
- Over the budget, the text parts are replaced by one summary part. With `Env.PutBlob` the full text is stored and a `transcript.Part{Stored}` follows the summary. A `PutBlob` error does not fail the call: the result is gated without the reference and the error is in `Summary.StoreErr`.
- The client still sees the full text: when the result had no `Content`, the full text becomes its `Content`.
- `Split` removes `accept_large_output` from an argument and returns its value. `Summary.Text()` is neutral wording for a dialect with none of its own.

### batch

- `Run` takes a `Dispatcher` (`Plan` and `Run` functions) from the caller, so a call in a batch goes through the same repair, validation, permission and gating as a call on its own. Refusing a batch inside a batch is the dispatcher's job.
- Scheduling: read-only calls run together and beside writes. Two writes that share a path, or of which one names no paths, run in the order given. A call that executes runs after everything before it and before everything after it.
- One failing call does not stop the others. After a cancel, calls that have not started are not started and are `cancelled`.
- Up to `max_calls` run at once. There is no separate concurrency limit.

## Defaults and their sources

| key | default | source |
|---|---|---|
| `tools.files.confine` | `false` | the review above |
| `tools.files.read_max_bytes`, `read_default_lines` | 256 KB, 2000 | Claude Code's Read |
| `tools.files.image_max_bytes` | 5 MB | Anthropic Messages API image limit |
| `tools.files.edit_max_bytes` | 4 MB | none: chosen here |
| `tools.max_output_bytes` | 1 MB | none: chosen here |
| `tools.shell.program` | `bash` | both upstream shell tools |
| `tools.shell.timeout`, `max_timeout` | 2m, 10m | Claude Code's Bash |
| `tools.shell.pipe_wait` | 2s | Codex's exec |
| `tools.gate.budget_tokens` | 25000 | Claude Code's `MAX_MCP_OUTPUT_TOKENS` |
| `tools.gate.bytes_per_token` | 4 | OpenAI's rule of thumb for English |
| `tools.batch.max_calls` | 10 | jcode's batch |

The upstream figures in this table were written from memory. None was checked against the captured prompts or the upstream source. They need checking against `prompts/` once the capture lane's files are in, and the two marked "chosen here" have no source at all.

## Not done, and not checked

- No output was compared with a recording from the pinned upstream CLI. There are no adapters and no recordings yet, so the tests check this lane's own typed results.
- No benchmark was run, and nothing uses `bytebufferpool`. Shell and search output are assembled in ordinary slices.
- Nothing was run on macOS. The darwin process-group file compiles. Its handling of `EPERM` from `kill` on a group of zombies is from memory of macOS behaviour and is untested.
- Nothing is wired into the loop, the session or `src/cli`. No `tools.Tool` values are built here.
- The `repair` tests use a schema written for the test, not a captured upstream schema. The `gate` tests use a `PutBlob` that writes files into a temporary directory, not the store.
- `go build ./...` and the whole-tree check were not run, by the lane rules.
- Outline and trace search modes, as said above.
