# Tools lane: capabilities, repair, gating, batch

2026-11-11

One implementation per capability, as plain Go functions with typed input and a typed result. Nothing here has a model-facing name, schema or wording. The dialect adapters wrap these in the next wave.

## What was built

| package | entry points | does |
|---|---|---|
| `src/tools/fsops` | `Read`, `ReadText`, `Write`, `ApplyEdits`, `Remove`, `Roots` | line-range read with image and binary detection, whole-file text read, whole-file write, exact string replacement (one or many edits), removal of one file |
| `src/tools/shell` | `Run` | one command in its own process group, output streamed through `Env.Progress`, timeout, cancel |
| `src/tools/search` | `Grep`, `Find` | text search and file listing over `rg` |
| `src/tools/repair` | `Compile`, `Schema.Apply` | the listed argument repairs, then schema validation |
| `src/tools/gate` | `Split`, `Apply`, `Estimate` | withholds a result over the token budget |
| `src/tools/batch` | `Run`, `Outcome` | several calls in one, scheduled by `Effect` |
| `src/tools/skill` | `Load` | one skill by name, over `agentctx.LoadSkill` |
| `src/tools/content.go` | `TextContent` | text as `acp.ToolCallContent` |
| `src/config/tools.go` | `Tools` | every limit and timeout used above |

A failure the model can act on is a typed error (`*fsops.Error`, `*shell.Error`, `*search.Error`, `*repair.InvalidError`, `*batch.Error`, `*skill.Error`) with a `Kind` and the numbers an adapter needs to write the upstream message. Any other error means the harness could not do the operation.

## Decisions

### Path confinement is off by default (changed after review)

The first version refused every path outside the working directory and the additional directories. The coordinator had it changed, for three reasons: `docs/design.md` leaves sandboxing to the host, the shell reaches every path anyway so the check protected nothing, and the upstream Read description tells the model it can read any file on the machine.

- `tools.files.confine` (default `false`). Off: read, write, edit, the shell `Dir` and the search path take any absolute path, and a relative path is taken from `Cwd`.
- On: a path that ends up outside every session directory, once symbolic links are followed, is `KindOutside`. This is the first version's behaviour unchanged.
- `Roots.Contains(path)` says whether a path is inside the session directories whatever the setting. Nothing in this lane acts on it. It is for the adapters and the permission prompt.
- There is no third mode.

File access goes through `os.Root` in both modes. Inside a session directory the root is that directory, so a link swapped in after the check cannot lead out. Outside, the root is the path's parent, or the deepest directory of it that exists when the file is new.

A link that points nowhere cannot be written through in either mode: the write fails rather than create the link's target.

### fsops

- Read counts lines by `\n`. A last line without a newline is a line. The range is refused whole (`KindTooLarge`) when it is over `read_max_bytes`. It is never cut.
- Binary: a NUL byte in the first 8000 bytes (git's rule), or text that is not valid UTF-8. Latin-1 files are therefore refused as binary. An adapter that needs to read them needs a decision on encodings first.
- Image: `http.DetectContentType` on the first bytes, for PNG, JPEG, GIF and WebP. The extension is not used.
- Write and edit put the content in a temporary file beside the target and rename it. A reader sees the old content or the new. The cost: the file gets a new inode, so other hard links keep the old content, and owner and extended attributes are not carried over. The mode is kept.
- Edit: each edit sees the result of the ones before it. `Old` must occur exactly once unless `All` is set. Any failing edit means nothing is written. Edits that leave the file as it was are `KindNoChange`.
- `Change.Diff()` returns the ACP diff content (old and new text). No unified diff text is produced: ACP clients diff the two texts themselves. An adapter whose upstream tool prints a patch has to render one.
- `ReadText` and `Remove` were added for the Codex `apply_patch` adapter. `ReadText` returns a whole text file up to `edit_max_bytes`, where `Read` is line-ranged and capped by `read_max_bytes`. `Remove` deletes one regular file and returns a `Change` with `Removed` set and the old text. It refuses a directory, and a file over `edit_max_bytes`, since its old text could not be shown.
- ACP's diff content cannot say a file was removed. A removal's `Diff()` is the old text against empty new text, the same as emptying the file. The adapter has to say it in the call's title or kind.
- A move is a `Write` to the destination and a `Remove` of the source. Nothing is atomic across files: a patch of several files that fails half way leaves the earlier files changed.
- A path that is a symbolic link names its target, for `Remove` as for `Write`: the target is removed and the link is left.

### shell

- `Setpgid` puts the command in its own group. How it is stopped is the caller's choice, per call, with no default in the package: `Input.CancelGrace` for a cancel and `Input.TimeoutGrace` for a timeout. Zero sends `SIGKILL` to the group at once. Otherwise the group gets `SIGTERM`, and `SIGKILL` when the command has not exited by the end of the period. The coordinator decided the capability stays neutral and the dialect chooses: upstream Codex uses 50 ms on cancel and none on timeout.
- When the command exits within the grace period the group is still sent `SIGKILL`, so a child that ignored `SIGTERM` does not outlive the call. The command has been waited for by then, so its process id is free: that kill could reach another group only if the kernel reused the id for a new group leader in between.
- `Result.StopSignal` says how a cancelled or timed-out command was stopped: `terminated` when it exited within the grace period, whether it died of the signal or caught it and exited, `killed` when it was sent `SIGKILL`, empty when it ended on its own. `Result.Signal` is still the signal the command died of.
- `Input.MaxOutputBytes` lets a call keep less output than `tools.max_output_bytes`. More than the configured size is an error, not a clamp.
- A process that leaves the group (`setsid`) is not killed. It can also hold the output pipe open, so reading stops `pipe_wait` after the command has ended and the result sets `PipeHeld`.
- Standard output and standard error share one pipe, so their order is kept and they cannot be told apart afterwards.
- `Result.Started` is false only when the context was already cancelled before the command was started. `Result.Outcome()` maps that to `cancelled`, a cancel after the start to `unknown`, a timeout or a non-zero exit to `failed`.
- Output over `tools.max_output_bytes` keeps the first half and the last half and reports `DroppedBytes`. The client still gets all of it through `Progress`.
- Each `Progress` call carries only new output, cut so that a multi-byte character is not split. A `Progress` error stops the streaming, not the command, and is returned in `Result.ProgressErr`.
- The command inherits the harness's environment and has no standard input.

### search

- `rg` is looked up with `exec.LookPath` on every call. Missing is `KindNoRipgrep` with a message that says how to fix it. There is no fallback.
- Lines mode reads `rg --json`, so paths and lines that are not UTF-8 survive. Files and counts modes read NUL-separated output.
- `--no-config` is always passed, so a user's `RIPGREP_CONFIG_PATH` cannot change results. Results are in path order. Lines mode has `rg` sort them, which makes `rg` single-threaded but lets the search stop at the limit. Files and counts modes let `rg` search in parallel and sort the list here (see `2026-11-12-search-sort.md`).
- `rg` does not follow symbolic links. A link out of the tree is not searched unless it is the search path itself.
- `Limit` and `Offset` count result lines, context lines included. Results past `tools.max_output_bytes` stop the search and set `Cut`.
- `rg` exit status 2 with nothing on standard error means some files could not be read: the result is returned with `Unreadable` set. With text on standard error it is `KindInvalid` (a bad pattern, glob or type).

Outline and trace modes are not built. The design says they need a separately specified implementation. Nothing here claims `rg` can do them.

### repair

The repairs are the design's list and nothing else: a list or an object sent as a JSON string, one object where a list is declared, a number or a boolean sent as a string. A repair is made only where the value's type is one the schema does not take, so a string stays a string wherever a string is allowed. Each repair is returned as a `Repair{Kind, Path}`. This package does not count or log: the caller does, with the returned list.

- An argument with no repairs is returned byte for byte. A repaired one keeps the member order and the text of every untouched value.
- Validation is `github.com/google/jsonschema-go`. It was enough. It ignores `format`, by its own documentation.
- To find a value's schema the walker follows `properties`, `additionalProperties`, `items`, `prefixItems`, `allOf`, `anyOf`, `oneOf` and local `$ref` into `$defs` or `definitions`. It does not follow `if`/`then`/`else` or `patternProperties`: a value under those is not repaired and is still validated.
- A string holding `null` is not repaired.

### gate

- The estimate is the result's text bytes divided by `bytes_per_token`, rounded up. Images and audio are not counted.
- Over the budget, the text parts are replaced by one summary part. With `Env.PutBlob` the full text is stored and a `transcript.Part{Stored}` follows the summary. A `PutBlob` error does not fail the call: the result is gated without the reference and the error is in `Summary.StoreErr`.
- The client still sees the full text: when the result had no `Content`, the full text becomes its `Content`.
- `Split` removes `accept_large_output` from an argument and returns its value. `Summary.Text()` is neutral wording for a dialect with none of its own.

### batch

- `Run` takes a `Dispatcher` (`Plan` and `Run` functions) from the caller, so a call in a batch goes through the same repair, validation, permission and gating as a call on its own. Refusing a batch inside a batch is the dispatcher's job.
- Scheduling is the loop's own rule for parallel calls (`loop.Conflicts`), after the loop lane asked for the two to match. A call that executes runs after everything before it and before everything after it, and so does a write that names no paths. Two writes that share a path run in the order given. A call that reads a path (`Plan.ReadPaths`) does not overlap one that writes it. Calls that only read run together. Paths are compared as text.
- One failing call does not stop the others. After a cancel, calls that have not started are not started and are `cancelled`.
- Up to `max_calls` run at once. There is no separate concurrency limit.

### skill

- `Load(ctx, skills, maxBytes, Input{Name})` takes the session's listed skills (from `agentctx.ListSkills` or `agentctx.Load`) and the size limit from the caller, which passes `context.max_file_bytes`. This package reads no config.
- The result has the skill's text after its front matter and its directory, so the model can read the files beside it.
- `*skill.Error` kinds: `empty_name`, `unknown` (with the names that exist) and `too_large` (size and limit). They are made from `agentctx.UnknownSkillError` and `agentctx.LimitError`. Any other error, such as a skill whose file is gone or has no front matter, is the harness's failure.
- The file is read on every call, so an edit to a skill shows without a new session. A name is matched against the listed names only. It is never used as a path.

### Codex figures, checked against the pinned commit

Read on 2026-11-11 from `raw.githubusercontent.com/openai/codex/ce0323f2f2d3b25e82806cd555237da3db4e1897/` (the short hash resolved with `gh api repos/openai/codex/commits/ce0323f2`). Paths are under `codex-rs/`.

- Confirmed: the 2 second pipe drain, 4 bytes per token rounded up (`truncate.rs:96`), and 1 MiB of kept output split half from the start and half from the end (`core/src/unified_exec/head_tail_buffer.rs:18`). The 1 MiB figure was written here as having no source. It has one.
- Wrong before: the comment said both upstream shell tools describe their command as bash. Codex does not fix the program. It runs the user's shell and falls back to bash, then zsh, then `/bin/sh` on Linux (`shell-command/src/shell_detect.rs:363`). The default stays `bash` and the comment now says it has no upstream source. Whether to use the user's shell is a decision for the Codex adapter.
- Different, and left as it is:
  - Codex's default command timeout is 10 seconds (`core/src/exec.rs:63`), ours is 2 minutes from Claude Code's figure. The Codex adapter has to pass its own timeout.
  - Codex's limit on one command's output for the model is 10000 tokens (`core/src/unified_exec/mod.rs:74`), ours gates at 25000.
  - On cancel Codex sends `SIGTERM` to the group, waits 50 ms and then kills (`core/src/exec.rs:71` and `:1043`). On timeout it kills at once (`:1036`). `shell.Run` kills at once unless the call passes a grace period, so the Codex adapter passes `CancelGrace` of 50 ms.

### Claude Code figures, checked against the 2.1.280 bundle

Read on 2026-11-11 from the capture lane's unpacked copy of the 2.1.280 bundle (2196 modules, minified). A citation is module, line and a text to search for. Identifiers are minified and change with every version, so they are not cited. The copy is in a scratch directory, not in the repository: the citations can be followed again only by unpacking the same release.

- Confirmed:
  - Command timeout: 120000 ms by default and 600000 ms at most (`chunk-dk0eh9zy.js:14`, `BASH_DEFAULT_TIMEOUT_MS`). The two environment variables override them, and the maximum is never below the default.
  - Lines read when the call names no limit: 2000 (`chunk-58pe6gjn.js:12`, `Reads up to`).
  - Read size: 262144 bytes (`chunk-esax8p5m.js:11`), the default `maxSizeBytes` in `chunk-fg23k495.js:11`.
  - 25000 tokens: the default limit on an MCP tool's result (`chunk-8ren4cq6.js:11`) and on one file read (`chunk-fg23k495.js:11`).
- Wrong before, corrected: the image limit was 5 MB with the API as its source. The API's limit is 5242880 bytes of base64, and upstream aims at 3932160 bytes of file, three quarters of it (`chunk-6bcrsx06.js:11`). A file of 5 MB would have been refused by the API. The default is now 3932160.
- Different, and left for the Claude adapter or a decision:
  - Read size. Upstream compares 262144 with the size of the whole file, and only when the call names no limit. With a limit it allows the selected lines 128 times the token limit in bytes (`chunk-fg23k495.js:11`, `=128`, used at `chunk-1xqpf2j8.js`, `maxSelectedBytes`). After either, the text must be within 25000 tokens, or the read fails with `File content (N tokens) exceeds maximum allowed tokens`. `fsops.Read` applies 256 KiB to what one read returns and counts no tokens.
  - Images. Upstream shrinks an image that is over 3932160 bytes or over 2000 by 2000 pixels, and fails only when it cannot (`chunk-n26k3byr.js`, `Unable to resize image`). `fsops.Read` refuses an image over the limit and changes none. Shrinking needs an image library, which is a dependency to decide on.
  - Command output. Upstream limits it to 30000 characters, raised to at most 150000 by `BASH_MAX_OUTPUT_LENGTH` (`chunk-s5969tjt.js:11`). It keeps the start only and appends `... [N lines truncated] ...` (`chunk-1xqpf2j8.js:683`). `shell.Run` keeps 1 MiB, half from each end. The Claude adapter has to cut the text it renders. No config key holds the 30000 yet.
  - Stopping a command. Upstream sends `SIGTERM` to the group and to the descendants it finds, and `SIGKILL` after 1500 ms, checking every 100 ms whether they are gone (`chunk-1xqpf2j8.js:19`, `=1500`, and `chunk-hjkwb4jc.js`). A timeout and a cancel take the same path. The Claude adapter passes 1500 ms as both `CancelGrace` and `TimeoutGrace`.
  - Shell program. Upstream takes `CLAUDE_CODE_SHELL`, then `SHELL` when it names bash or zsh, then looks for both in four directories (`chunk-1xqpf2j8.js:675`). The default here stays `bash`.
  - Edit size. Upstream's Edit takes a file of up to 1 GiB (`chunk-1xqpf2j8.js:3451`, `too large to edit`). `edit_max_bytes` is 4 MiB because both texts are held for the diff.
- Edit rules, compared with `fsops.ApplyEdits` (`chunk-1xqpf2j8.js:3451` to `3453`):
  - The same: `old_string` equal to `new_string` is refused, a string that is not found is refused, and more than one match without `replace_all` is refused.
  - Missing here: upstream refuses an edit of a file the session has not read (`File has not been read yet`), and of a file changed since it was read (`File has been modified since read`). That needs what was read and when, kept per session. No capability keeps it.
  - Not compared: upstream retries a failed match with quote characters and `\uXXXX` escapes swapped. The adapter tests against the recorded outputs will show whether that matters.
- Not found in the bundle: a limit on the length of one line of a read. The Read prompt of this version does not mention one, and a search of the read modules for a line limit found none. `fsops.Read` has none either.

The jcode figure for `tools.batch.max_calls` is still from memory.
