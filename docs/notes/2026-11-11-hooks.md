# Hooks

2026-11-11

## Built

`src/hooks`: runs the commands configured under `[[hooks]]`. `src/config/hooks.go`: the `Hook` type and its validation.

```toml
[[hooks]]
event = "pre_tool"            # pre_tool | post_tool | prompt | stop
tools = ["Bash", "shell"]     # empty: every tool. Must be empty for prompt and stop
command = ["/usr/local/bin/check-cmd"]
timeout = "10s"               # required
max_output_bytes = 65536      # 0: no limit
```

The loop calls one function per event on a `*hooks.Runner` made by `hooks.New(cfg.Hooks)`:

```go
PreTool(ctx, session, callID, tool string, input jsontext.Value) (Decision, error)
PostTool(ctx, session, callID, tool string, input jsontext.Value, outcome transcript.Outcome, parts []transcript.Part) (Decision, error)
Prompt(ctx, session, parts []transcript.Part) (Decision, error)
Stop(ctx, session, reason string) (Decision, error)
```

`Decision` has `Action` (`allow` or `deny`), `Reason`, and for `PreTool` the `Input` to run the call with. The loop can act on `Decision` alone. The error is for the log.

## Protocol

The command is run as configured, with no shell, in the session's working directory, with the harness's environment. One JSON object on stdin:

```json
{"event":"pre_tool","session_id":"…","cwd":"/abs","tool":{"name":"Bash","call_id":"…","input":{…}}}
{"event":"post_tool", …,"tool":{…},"result":{"outcome":"completed","parts":[{"text":"…"}]}}
{"event":"prompt", …,"prompt":[{"text":"…"}]}
{"event":"stop", …,"stop_reason":"end_turn"}
```

One JSON object on stdout, with exit status 0:

```json
{"decision":"allow"}
{"decision":"deny","reason":"why"}
{"decision":"allow","input":{…}}
```

`input` is accepted only from a `pre_tool` hook.

## What a failure means

Every failure is a deny, with an `*hooks.Error` whose `Kind` says which one. Nothing fails open.

| what happened | `Kind` | decision |
|---|---|---|
| the command cannot be started | `start` | deny |
| non-zero exit, whatever was printed | `exit` | deny |
| killed by a signal we did not send | `exit` (`ExitCode` -1) | deny |
| still running, or a process it left still holds its output, at the timeout | `timeout` | deny, group killed |
| the context was cancelled | `cancelled` | deny, group killed |
| empty output, not JSON, two values, unknown member, unknown decision | `output` | deny |
| deny with no reason, allow with a reason, deny with an input, input outside `pre_tool` | `output` | deny |
| stdout over `max_output_bytes` | `output` | deny |

Why deny in every case: a hook is put there to stop something. If a crashed or slow hook allowed, the way to get past a guard would be to make it crash or stall. An operator who wants a hook that never blocks writes one that always prints allow.

Why a non-zero exit denies even with a valid allow on stdout: the exit status is the one thing a script sets when it fails half way, and `set -e` scripts print before they fail.

Why unknown members are rejected: a hook written for another harness's protocol (for example one that answers `{"continue":true}`) would otherwise be read as having no decision or, worse, as an allow.

What a deny means per event, for the loop to carry out:

- `pre_tool`: the call is not run. The reason is the call's failed result.
- `post_tool`: the call already ran. The reason replaces the result, as a failed call.
- `prompt`: the turn does not start. The client gets the reason.
- `stop`: the turn does not end. The model gets the reason and continues. The loop needs its own bound on this, or a stop hook that always denies never lets a turn end.

## Decisions

- Hooks of one event run in config order, one at a time. The first deny ends the run. A `pre_tool` hook that changes the input passes the changed input to the hooks after it.
- A changed input is returned as is. The loop validates it against the tool's schema like the model's input, since the hook is not trusted to produce a valid one.
- `timeout` has no default. Hooks are a list, and the rule is that a list has no defaults, so each hook states its own. A hook without one is a config error. No number has been measured to be right for everyone.
- `max_output_bytes` 0 means no limit, for the same reason the context limits do. A hook that writes more than the limit to stdout returns to the loop `Decision{Action: Deny}` with the failure as its reason, and an `*hooks.Error` of kind `output` whose detail gives the size written and the limit. This holds even when the first bytes are a complete allow: a cut-off answer can still parse, so the answer is not read at all. Stderr over the limit is not a failure. The excess is dropped and counted in `Error.StderrDropped`.
- Each command runs as the leader of its own process group. On timeout or cancel the group gets `SIGKILL`, not a signal it could ignore. `group_linux.go` and `group_darwin.go` hold it. macOS answers `EPERM` when only zombies are left, which is not an error there.
- The pipes are made with `os.Pipe` and not left to `os/exec`, so that `Wait` returns when the command exits even if a child still holds a pipe. A hook that exits and leaves such a child has not finished its answer, so it runs into the timeout.
- Stdin is written from a goroutine and a broken pipe is ignored: a hook need not read its input.
- Tool names match exactly, as the model calls them. No patterns.

## Not done

- Nothing calls the runner. The loop lane adds the four calls.
- `Config.Hooks` is in `config.go` (added by the coordinator), which calls `validateHookList`. `src/hooks/config_test.go` loads `[[hooks]]` from a TOML file. YAML and JSON files are not tested.
- Hooks are not in the `_meta.acpharness` allowlist, on purpose: a client should not be able to add or remove a guard.
- Nothing runs on macOS. It builds.
- No environment variables are added for the command. Everything is in the JSON.
