# Upstream capture: Codex ce0323f2 and Claude Code 2.1.280

2026-11-11. Scripts are in `tools/capture/`, output in `prompts/`.

## Codex

`uv run tools/capture/codex.py` clones openai/codex at `ce0323f2`, copies the
listed files unchanged into `source/`, and builds a test module
(`codex_probe.rs`) inside codex-core that calls upstream's own tool planners
and the interruption marker function. Output: `prompts/codex/ce0323f2/`.

- `instructions/`: the instruction template per catalog model, from `models.json`.
- `tools/specs/`, `tools/requests/`: tool specs and the tool list per model and profile.
- `interruption/`: the turn-aborted marker for both roles.
- `source/`: upstream files, byte for byte.

Limits, also in the manifest: no extension, MCP or dynamic tools. Linux only.
JSON member order is the test build's, so compare as JSON values.

## Claude Code

The npm package `@anthropic-ai/claude-code` is a launcher. The program is a Bun
single-file executable in `@anthropic-ai/claude-code-linux-x64`.

`uv run tools/capture/claude_code.py` does not run it. `bunfs.py` reads the
embedded modules from the ELF `.bun` section. `jseval.py` evaluates upstream's
own prompt builders over constants with tree-sitter, and `zodschema.py` ports
the bundle's zod to JSON Schema conversion. A value only a session has is
unknown. A condition on it is taken both ways and each distinct text is written
as a `.vN` variant, with the conditions in the manifest. An item with a path
that cannot be evaluated is not written and is listed under `not_captured`.

Output: `prompts/claude-code/2.1.280/`, 112 files. Two runs are byte identical.

- `interruption/`: `[Request interrupted by user]` and the tool-use form.
- `system/identity.*`, `system/leading.*`, `system/section.*`: single sections.
- `tools/`: 67 tools as `{name, description, input_schema}`.
- `package/sdk-tools.d.ts`: copied from the launcher tarball.

Not captured, with reasons in the manifest (38 entries):

- Tools: Bash, Read, Agent, WebFetch, WebSearch, EnterPlanMode, SendMessage,
  ScheduleWakeup, Workflow, PowerShell, the four Artifact tools, and ten tool
  definitions whose name is computed at run time.
- 14 system sections. There is no whole assembled system prompt, and no
  measured mapping from model to variant.

The per-item search budget is 48 combinations. Raising it to 4096 did not
finish in 50 minutes, so the items over budget stay listed as gaps.

## Recording from the executable

`claude_code_record.py` and `claude_code_sandbox.py` run the executable in a
bubblewrap sandbox against a recording server in the same sandbox. The root is
built from nothing: `/usr` is a copy of the 88 entries in
`sandbox_runtime.json` (interpreter, loader, seven libraries, the standard
library files the script loads), each checked by sha256; `/input` is read-only;
`/work` is the only writable path. The probe compares the root, `/usr`,
`/input`, the environment, host name and interpreter state with exact expected
values, and the host repeats the comparison. The host reads the sandbox's
result without following symlinks and writes its report where the sandbox has
no access. Recorded requests are scanned for credentials and host paths.

The executable has been run once, after review, as `-p hi
--dangerously-skip-permissions`. It sent two identical `POST /v1/messages`
requests with the placeholder key and exited when the server answered 400. The
raw request is kept out of the repository: it holds sandbox paths, the capture
host's kernel release and identifiers generated for the run. `hostscan.py`
classifies those, and `claude_code_request.py` extracts only the tools list and
refuses any tool with a match.

`prompts/claude-code/2.1.280/profiles/print-sdk.default.claude-opus-5-5/` holds
that extraction: 19 tools as `{name, description, input_schema}`, with
provenance and hashes in its manifest.

- It adds Agent, Bash, Read, ScheduleWakeup, SendMessage, WebFetch and Workflow,
  which the static capture lacks.
- The other 12 equal the static capture exactly. Edit and Write equal the `v1`
  variant.
- WebSearch is withheld: its description states the month of the run.
- Scope: print mode, default settings, the executable's default model. It has
  no Glob, Grep, TodoWrite or Task tools. No other mode or model was recorded.

Still missing: the assembled system prompt, per-model differences and recorded
tool outputs (`outputs/`).

The capture scripts build in scratch and install with `outdir.py`, which
changes only files that differ. An earlier version emptied its destination
while it ran.

## Diff against another release

`uv run tools/capture/diff.py <old capture> <new capture>` prints removed,
added and changed files and changes to the gap list.

Static capture of 2.1.304 against 2.1.280: 28 files removed, 11 added, 15
changed, 68 the same. The 2.1.304 run wrote no system sections: the marker
used to find the prompt assembler matches two functions there, so
`claude_code.py` needs a better locator before it is used on that release.

## Cross-check against nanocode

nanocode (`0e6c253da`) pins Claude Code 2.1.304 on darwin-arm64, recorded from a
live CLI against a local stub, and Codex `c6e4438a`.

Claude, comparing its 11 recorded tools with a static capture of 2.1.304:

- Equal in description and schema: Edit, Write, TaskCreate, TaskList (the `v1`
  variant of each), TaskGet, TaskUpdate, TaskStop.
- Not comparable, because the static capture has none: Bash, Read, WebFetch,
  WebSearch.
- Only in the static capture: every other tool. nanocode recorded a chosen
  `--tools` list, not the full set.
- Its identity block equals one of the 2.1.280 identity files. Five 2.1.280
  section files appear whole inside its second system block.

Codex:

- The three instruction templates it pins (gpt-6-astra, gpt-6.1-sol,
  gpt-6-luna) have the same sha256 and length as this capture's.
- Six of its nine pinned source files are in this capture with the same
  bytes, although the commits differ. The other three
  (`codex-rs/tools/src/responses_api.rs`, `tool_spec.rs`,
  `json_schema/types.rs`) are not in this capture's list.
- Its tool definitions are Rust code, not JSON, so the specs were not compared.
