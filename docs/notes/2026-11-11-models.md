# Models: config, resolution and the session's model option

2026-11-11

## Config (`src/config/models.go`)

`Model` has `chain`, `context_window`, `max_output_tokens`, `family` and `dialect`. `ParseChainEntry` parses `provider:account/model`: the provider ends at the first `:` and the account at the first `/` after it, so a model name may hold both (`openrouter:main/anthropic/claude-opus-4.7:beta`).

`validateModelSet` refuses: an empty chain, an entry that does not parse, an account that is not configured, an account whose provider is not the entry's, a provider that is neither built in (`claude`, `codex`) nor configured, a `default_model` that names no model, a negative figure and a dialect that is not `claude`, `codex` or `generic`. Models are checked in name order, so one config always reports the same error.

No model at all is valid. An empty `default_model` beside configured models is refused: it names no model, and picking one for the user would be a silent default.

Validation does not look at metadata. Whether a model's figures are known is checked when the model is selected, as the design says.

## Resolution (`src/models`)

- `Select(defaultModel, configured, name)` resolves the model a session chose. An empty name is the default. Typed errors: `*NoModelError`, `*UnknownModelError`, and those of `Resolve`.
- `Resolve(name, cfg)` parses the chain and gives each entry its `Metadata` (context window, max output, family). A figure in the config replaces the built-in one for every entry of that chain. An entry that still lacks a figure is a `*MetadataError` that lists the config keys to set.
- `Model.Chain(clients)` returns the `router.Entry` values, with the client for each entry's provider id from the caller. A provider without a client is a `*ProviderError`. `src/provider/router` is not changed.
- `DialectOf(family)`: `claude` gives `claude`, `gpt` and `codex` give `codex`, anything else gives `generic`. `models.<name>.dialect` wins over it.

Decisions:

- Metadata is per chain entry, because a fallback can move a request to an endpoint with a smaller window. The dialect is one value per model, because a fallback happens inside a turn and the tools cannot change there. A chain whose entries resolve to different dialects, with no `dialect` set, is a `*DialectError`.
- The table is matched on the exact model id. A gateway's name for a model (`anthropic/claude-opus-4.7` on OpenRouter) is another id and is not matched: the window that counts there is the gateway's. The chain in the design's sketch therefore needs `context_window`, `max_output_tokens` and `family` set until provider model listings are read.
- The family is required only when no dialect is pinned, since choosing the dialect is its one use here.
- The design's "dialect of the family the model was distilled from" has no table. No source for one was read, so such a model gets its dialect from config.

Limits of these figures:

- OpenAI's page prints the context window rounded, as "1.05M". The exact token count was not read.

- Left out on purpose: the GPT-5 family. jcode gives 272,000 and 1,000,000 by name prefix with a comment and no cited page, and its max output for them was not found. Claude 4.5 and older, and jcode's "version 5 and later is 1M" guess for generations it has not verified.

## Session (`src/session/model.go`)

`session.AddModels(registry, defaultModel, configured)` registers:

- the `model` config option, category `model`, a select over the configured names in name order, starting at the default;
- the `model` key of `_meta.acpharness` on `session/new`;
- the `/model` command: without an argument it shows the model and the configured names, with one it switches.

The chosen name is written to `loop.Turn.Model` (loop commit eec60f8) before each turn, so a switch applies from the next turn. Each of the three ways goes through `models.Select`, by a new `ConfigOption.Validate` hook, so a model whose metadata is not known is refused with `-32602` when it is chosen and the session keeps its model. A default that cannot be resolved fails `AddModels`. With no model configured, `AddModels` registers nothing.

Every configured name is listed, including one that would be refused. Hiding it would leave a user with a model in the config that never appears and no error to say why.

## What does not work yet

The loop does not read `Turn.Model`. `loop.New` takes one provider and one tool set, so a switch changes the field and nothing a model does. `AddModels` must not be called in `serve` until the turn picks its chain and tool set per turn from `Turn.Model`: registering the option is what advertises it. The loop lane said the same to the coordinator.

Also not done: rewriting earlier tool calls when a switch changes the dialect, dropping provider-native items that cannot transfer, provider model listings (`/models` on OpenRouter), and subagent spawns that name a model.
