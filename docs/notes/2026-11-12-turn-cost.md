# Turn cost: cached schemas, a pooled request body, and `store.fsync`

Date: 2026-11-12

## Profile this came from

Sixty turns in ten sessions of one `towa serve` process, against `openai/gpt-oss-20b` on LM Studio, with `telemetry.pprof.address` on. The model was loaded with an 8,192-token context, so `context.default_agents` and `context.default_skills` were off and prompts were small. towa used about 26 ms of CPU and 2 MB of allocation a turn. Of the CPU samples, 45% were reading the model's stream, 17% storing entries (15% in fsync), 15% sending ACP updates, and 5.6% compiling tool schemas. Compiling schemas was 17% of allocation and encoding the request body 23%.

## What changed

- **Schemas.** `loop.Resolved` has a `Schemas` field. The command line fills it with the compiled schemas `toolset.Assemble` already returns, which come from the process-wide `toolset.Cache`. The loop compiled every tool's schema again at the start of each turn. It still does when `Schemas` is nil, which is how the loop's own tests run.
- **Request body.** The chat client encodes its request into a `bytebufferpool` buffer and returns it after the response is closed, as the Anthropic and OpenAI clients already do.
- **`store.fsync`**, on by default. Off, `src/store/dir` calls fsync for nothing: not the log, the metadata, a blob or a directory. A crash of the machine can then lose the last writes or tear the last record, and the next open reports a torn log as before. A crash of the process alone loses nothing, since the writes are in the page cache. `dir.Options.NoSync` is the option, and `TestNoSyncStoreDoesNotFsync` covers it.

## Measurements

Benchmarks in scratch, built with `go test -overlay`, old and new run alternately twice:

| | Before | After |
|---|---|---|
| Compile the 7 core tools' schemas, once a turn | 0.61 to 0.69 ms, 189 KB, 4,759 allocations | not done |
| Encode a 33 KB request body | 189 to 203 µs, 276 KB | 128 to 143 µs, 76 KB |

Thirty live turns in five sessions, each build run twice. The runs are not identical, because the model chooses its tool calls, and between 3 and 8 turns of each run failed on the model's context size.

| | Before | After | After, `store.fsync=false` |
|---|---|---|---|
| Allocated over the run | 48.9 and 64.4 MB | 32.7 and 36.2 MB | 40.9 MB (one run profiled) |
| Schema compiling under the loop | 9.7 and 13 MB | none | none |
| CPU, user plus system | 650 ms, and 2,330 ms in a run with 1,820 ms of system time | 650 and 740 ms | 660 and 640 ms |

CPU over thirty turns did not move outside the noise between runs. The gain that shows is allocation.

fsync, counted with `strace -c` over six turns with eight tool calls and one session creation: 31 calls, 232 µs each, 7.2 ms in total. That is about five calls and 1.2 ms a turn on this machine's disk. A slower disk makes the key worth more.

## Not done

- `toolset.Assemble` still runs every turn. Its cache hit should cost little, but profiles of the new build show 0.5 to 3.5 MB under `toolset.prepare` over thirty turns, more than one compile of each schema. Whether some schema misses the cache is not traced.
- One write per ACP update, and the model stream's reads and JSON decoding, are the rest of the CPU.
